# BudgetCC

A deterministic, trace-driven congestion-control testbed in C++17 that replays cellular delivery traces (Mahimahi format), runs five controllers (Reno, Cubic, BBR-lite, GCC-lite, BudgetCC) over the same transport, and evaluates BudgetCC, a controller that takes an application one-way-delay budget as input. Per-interval telemetry goes to Loki and Grafana. The build is staged: Phase 1 is a deliberately unoptimised baseline, Phase 2 optimises the algorithm and the code and re-runs the identical experiments.

## Headline: Phase 1 vs Phase 2

BudgetCC (D = 150 ms, deep buffer, median of 10 traces) and the engineering metrics. Full tables, per-trace numbers and
hypothesis checks: [docs/results.md](docs/results.md) (generated by `tools/analysis.py doc` from `results/*.json`).

| Metric | Phase 1 | Phase 2 | Change |
|---|---|---|---|
| M2 p95 one-way delay | 308.4 ms | 132.2 ms | 57% lower (92-93% below Cubic) |
| M3 p99 one-way delay | 1,434 ms | 220 ms | 85% lower |
| M4 violation at D=150 | 13.13% | 2.23% | 83% lower; target (<= 5%) met on 9 of 10 traces |
| M5 recovery after a capacity drop | 3,430 ms | 770 ms | 78% lower |
| M1 utilisation | 92.9% | 83.0% | 9.9 pp **lower** (cost of the delay gain; Cubic/BBR-lite stay at 99%) |
| M7 simulation speed | 1.81 M events/s | 2.79 M events/s | 1.54x |
| M8 CPU per ACK | 104.4 ns | 68.2 ns | 1.53x |
| M9 allocations per packet | 4.945 | 0 | heap traffic removed |
| M10 matrix runtime (2 traces, 50 runs) | 100.7 s | 0.3 s | 370x (Phase 1 BudgetCC scanned 10 s windows linearly) |

Engineering numbers come from one interleaved A/B session (`tools/bench_ab.py`, 3 rounds, medians, same machine).

## Quick start

Windows (MSVC developer prompt) / Linux:

```
python tools/check.py            # configure + build + ctest + pytest
build/<preset>/budgetcc run --algo cubic --trace step_down --buffer 1000
```

Presets: `windows-msvc`, `linux-gcc`, `linux-clang`, `asan-ubsan`, `tsan`, `release`, `dev-mingw` (local MSYS2 g++).

## Architecture

See `docs/design_source.md`. Sender (traffic source, transport, pacer, controller) -> link emulator (trace-driven bottleneck, drop-tail, propagation) -> receiver -> feedback. Telemetry: 10 ms samples -> ring -> JSON lines / CSV -> Loki.

## Metrics

M1 utilisation, M2 p95 OWD, M3 p99 OWD, M4 budget violation, M5 recovery time, M6 Jain fairness, M7 events/s, M8 CPU per ACK, M9 allocations per packet, M10 matrix runtime. Definitions: `CLAUDE.md` section 4, decision 5, and `docs/decisions.md`.

## Limitations and claims

- The baselines are this project's own simplified implementations, not the kernel's.
- BudgetCC was not compared against SCReAM or Copa.
- Not claimed: first delay-budget controller.
- Phase 1 was intentionally unoptimised, so the engineering speedups are relative to it. Baselines also changed slightly from Phase 2 feedback batching (A3); BBR-lite p95 got 57% worse (723 -> 1,132 ms) because its delivery-rate filter sees 10 ms ACK bursts.
- BudgetCC trades utilisation for delay: 83.0% median, and only 17-63% on the bursty `tmobile_lte_*`, `verizon_lte_short` and `att_lte_driving_2016` traces (listed in docs/results.md as misses of the within-25-pp target). `att_lte_driving_2016` misses the 5% violation target. Raising the probe ceiling to 1.5 lifts utilisation but pushes violation to 8-11%, so the spec value 1.15 is kept.
- GCC-lite reaches only 14% utilisation on these traces; it is reported as measured and not tuned.
- Cut: A2 parameter sweep (run once on the tuning split, best k 0.25 / margin 0.1 / w_down 0.3, not applied), A4 adaptive margin, dashboard v2, Grafana screenshots (no Docker locally), fresh-clone reproduce, per-step retroactive benchmarks (`results/bench_history.jsonl` lines are indicative; the CPU speed drifts several-fold).
- Phase 2 binaries cannot reproduce `results/phase1.json`: check out tag `v0.1-baseline` for that.
- Tuning split (decision 9) was fixed but no tuned values were adopted.
