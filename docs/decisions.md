2. 12-byte RTP header, 16-bit seq unwrapped at receiver. 3. Window controllers: pacing = gain x cwnd/srtt. 4. Video mode per CLAUDE.md. 5. ## Implementation decisions

13. **Toolchain locally.** MSYS2 UCRT64 g++ 14.1 + CMake + Ninja (pip). Alt: MSVC. Reason: no Visual Studio or Docker or WSL distro on the development machine. MSVC, Clang, sanitizers and coverage run in CI only; they are unverified locally.
14. **Dependencies.** CI uses the vcpkg manifest (baseline `bf19794…`). Local builds fall back to CMake FetchContent at pinned tags (fmt 11.0.2, CLI11 v2.4.2, cpp-httplib v0.18.1, googletest v1.15.2). Alt: pacman packages. Reason: pacman install failed on a dependency conflict.
15. **Power plan.** Benchmarks run under the machine's active plan (recorded in `env.power_plan`), not switched to High performance. Alt: `powercfg /setactive`. Reason: changing system power settings was not requested; the plan is recorded so results are honest.

16. **Trace categories.** The Mahimahi README does not say which traces are stationary. The six real traces are `att_lte_driving`, `att_lte_driving_2016`, `tmobile_lte_driving`, `verizon_lte_driving` (named "driving" upstream) and `tmobile_lte_short`, `verizon_lte_short` (not labelled upstream). The "short" pair stands in for the non-driving category in decision 9; this is an assumption, not a measured property. Pinned commit `f1346c3`; the repository is GPL-3.0, so traces are fetched, never vendored.
17. **A2 tuning split (decision 9, fixed before any sweep).** Tune on `verizon_lte_short` (non-driving), `att_lte_driving` (driving), `sawtooth`, `step_down`. Report on the other four real traces plus `step_up` and `outage_2s`. Objective: maximise mean utilisation subject to violation_pct <= 5 at D = 150, deep buffer.
18. **Queue-delay ground truth.** `q_ms` is 0 when the queue is empty, otherwise `max(sojourn of the last dequeued packet, age of the head packet)`. Alternative: the last sojourn only. Reason: during an outage nothing is dequeued, so the last sojourn would hide a queue that is growing.
19. **M5 recovery.** Taken literally ("first time >= t where the queue stays <= Q* for 100 ms") the value is 0 whenever the queue is low at the event time, which is the case for every step-down because the event time precedes the drop. Implemented: from event time t, find the first sample with q > Q*; recovery is the time until q stays <= Q* for 100 ms after that. If q never exceeds Q* after t the value is 0. Events are detected on a 10 ms grid from t = 1 s. Alternative: literal definition. Reason: it would score every algorithm 0.
20. **Video frame sizing.** Delta frames are `mean x 60 / 63` and key frames `4 x` that, so the mean over one key interval equals `pacingRate / 30` and the key/delta ratio is exactly 4.
21. **Flow start jitter.** `--seed` derives (splitmix64) a start offset of 0-9 ms for flows after the first, so identical flows do not run in lock-step. Single-flow runs ignore the seed.
22. **Cubic fairness convergence.** Two identical Cubic flows on a deep-buffer 12 Mbps link reach Jain 0.971 after 60 s and 0.995 after 120 s. The unit test asserts <= 0.02 from 1.0 at 120 s and >= 0.95 at 60 s; the matrix fairness runs (60 s) report whatever they measure.
23. **BBR-lite omissions.** No ProbeRTT (min RTT comes from a 10 s window filter); delivery rate is a windowed rate over clamp(srtt, max(minRTT, 40 ms), 250 ms) instead of per-packet send-interval samples; Drain exits when the RTT is within 10% + 1 ms of the minimum (the congestion controller does not see sends, so BBR's inflight test is not available); ProbeBW phases last one minimum RTT and start at the first cruise phase; losses are ignored (as in BBR v1).
24. **GCC-lite scope and constants.** Inter-group delay (5 ms groups), trendline over 20 samples with smoothing 0.9 and gain 4, adaptive threshold (k_up 0.0087, k_down 0.039), 10 ms over-use time, AIMD with decrease to 0.85 x incoming rate, loss-based cap (>10% loss cuts, <2% grows 5%/500 ms). Multiplicative increase is 8% per 100 ms (standard GCC is 8% per second, which cannot reach 12 Mbps inside a 60 s run without bandwidth probing; probing is omitted). Start rate 1 Mbps. On bursty LTE traces this controller stays conservative and uses little of the link; that is a property of the baseline, reported as measured.
25. **RateWindow warm-up.** `RateWindow::rateBpsWarm` divides by the age of the data while the window is still filling (at least min(window, 20 ms)). Without it GCC-lite clamped its own rate to a fraction of the real incoming rate for the first 250 ms and never recovered on the LTE traces (utilisation 6-12%, found while testing).
26. **Controller probe.** `CongestionControl` gained a non-pure `probe()` returning a small struct (cwnd, capacity estimate, queue estimate, Q*, min RTT) for telemetry and tests. The required interface is unchanged.
27. **Windows MinGW build.** Linked statically (`-static`): a dynamically linked binary hung when started from a shell whose PATH put a different libstdc++/winpthread first.
28. **BudgetCC v0 start rate.** 1 Mbps, additive increase of one packet per RTT per RTT (rate-based), decrease x0.8 at most once per smoothed RTT, in-flight cap `rate x (rtt_min + Q*)`.
